# PRD: 팀 편성 웹 앱 (Team Former)

## 1. 목적

학생들이 팀 프로젝트를 위한 팀을 **스스로** 편성하는 웹 앱이다. 학생은 팀에 지원하고, 그 팀의 팀원들이 투표로 받아들일지 정한다. 모집을 마감한 뒤 팀이 없는 학생은 AI(OpenRouter)가 배정안을 만들고, 앱이 그 배정안을 규칙으로 검사한다. AI가 모두 실패하면 앱이 스스로 규칙을 지키는 배정을 찾는다.

- 배포: Streamlit Community Cloud
- DB: Supabase(PostgreSQL). 테이블 이름은 모두 `tf_`로 시작
- 채점: 자동 채점 프로그램이 화면 요소를 Streamlit `key`로 찾아 조작함. 결과 안내(`result`)의 첫 단어로 판정함

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생 (가상 명단의 학생) | 학번 + 비밀번호(모두 `1234`) | 팀 목록, 팀원, 팀원의 주 역할과 보조 역할 보기. 팀에 지원. 내 팀에 들어온 지원에 찬성 또는 거부 |
| 관리자 | 학번 `admin` + `ADMIN_PASSWORD` | 명단 CSV와 팀 수로 처음 상태 만들기. 모집 마감. AI 배정 실행, 배정안 확인과 확정 |

- 관리자 계정은 앱이 시작할 때 비밀 값 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 관리자 계정은 남는다.
- 실제 사람의 이름과 학번은 쓰지 않는다. 교수가 나눠 준 가상 명단만 쓴다.

## 3. 용어

- **역할 6개**: 기획자(PL), 웹 프로그래머(WP), 프론트엔드 디자이너(FD), 테스터(TT), 보고서 작성자(RW), 발표자(PT)
- **주 역할**: 학생마다 1개. 팀 안에서 중복을 따지는 기준이다.
- **보조 역할**: 학생마다 0~2개. 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다.
- **필수 포함 역할**: 기획자, 웹 프로그래머. 확정한 팀마다 **서로 다른 두 학생**이 하나씩 맡아야 한다(주 역할이든 보조 역할이든 상관없음).
- **막힘**: 지원 단추를 누른 순간 앱이 규칙 위반을 발견해 **지원을 접수하지 않은** 것
- **거절**: 접수되어 대기 중이던 지원이 떨어진 것. 원인은 세 가지로, 팀원의 거부, 승인 직전 재검사, 모집 마감이다.

## 4. 기능 요구사항

### 4.1 로그인 (FR-1)
- 학번과 비밀번호로 로그인한다. 비밀번호는 bcrypt 해시로 저장하고 비교한다.
- 비밀번호가 틀리면 로그인되지 않는다. 학번만으로는 남의 계정에 들어갈 수 없다.
- 로그인한 사람의 이름을 `whoami` 영역에 보여 준다.
- 학생 계정으로는 관리자 화면과 관리자 기능을 쓸 수 없다. 서버 쪽 함수에서도 권한을 검사한다.
- 구글 로그인(`st.login`)은 쓰지 않는다.

### 4.2 명단 올리기와 초기화 (FR-2, 관리자)
- 명단 CSV 파일과 팀 수를 넣고 "처음 상태 만들기"를 누른다.
- CSV는 BOM이 있는 UTF-8도 읽는다(`utf-8-sig`). 열은 `student_no,name,main_role,sub_roles`이고, 보조 역할이 2개면 `;`로 구분하며 없으면 빈칸이다.
- 지원, 투표, 팀원, 마감 표시, 배정안을 모두 지우고 명단의 학생과 팀1~팀N(빈 팀)을 만든다. 관리자 계정은 남긴다.
- CSV가 틀리면(열 부족, 6개 역할 밖의 값, 학번 중복, 보조 역할 3개 이상, 주 역할을 보조 역할로 중복 기재 등) 아무것도 바꾸지 않고 `막힘: 이유`를 보여 준다. 성공하면 `승인: 명단 N명, 팀 M개로 처음 상태를 만듦`을 보여 준다.

### 4.3 학생 화면 (FR-3)
- 팀마다 `team_{번호}` 영역에 팀 이름, 팀원 이름, 주 역할, 보조 역할을 보여 준다.
- 로그인한 학생의 팀에는 "내 팀"을 표시하고, 팀이 없으면 "아직 팀이 없음"을 보여 준다.
- 팀마다 지원 단추 `apply_{번호}`를 둔다. 이미 팀이 있거나, 결과를 기다리는 지원이 있거나, 모집이 마감되었으면 단추를 숨기거나 비활성화한다.
- 내 팀에 들어온 대기 중인 지원마다 찬성 `vote_yes_{지원자 학번}`, 거부 `vote_no_{지원자 학번}` 단추를 둔다. 이미 투표했으면 단추를 숨기고 "내 투표: 찬성/거부"를 보여 준다.
- 내가 낸 지원의 상태(대기, 승인, 거절과 이유)를 보여 준다.

### 4.4 지원 (FR-4)
지원 단추를 누르면 아래 순서로 검사하고, 하나라도 걸리면 `막힘: 이유`를 보여 준다. DB에는 기록하지 않는다.

| 순서 | 막힘 이유 |
|---|---|
| 1 | 모집이 마감됨 |
| 2 | 이미 팀이 있음 |
| 3 | 결과를 기다리는 지원이 있음 |
| 4 | 팀이 꽉 참 (4명) |
| 5 | 같은 주 역할의 팀원이 있음 |
| 6 | 필수 포함 역할을 맡을 학생의 자리가 모자람 (4.6) |

검사를 통과했을 때의 처리는 다음과 같다.
- **빈 팀**이면 바로 승인되어 팀원이 된다. 안내는 `승인: 팀N에 들어감`이다.
- **팀원이 있는 팀**이면 대기 상태로 접수된다. 안내는 `대기: 팀원의 투표를 기다림`이다.

### 4.5 투표 (FR-5)
- 투표할 사람은 **투표하는 때의 팀원 전원**이다. 지원 뒤에 새로 들어온 팀원도 투표한다.
- 한 명이라도 거부하면 다른 팀원을 기다리지 않고 **바로 거절**된다.
- 아직 투표하지 않은 팀원이 있으면 **대기**다.
- 지금 팀원 전원이 찬성하면 **승인 직전 재검사**(4.6의 정원, 주 역할 중복, 필수 포함 역할 자리)를 한다.
  - 통과하면 승인되어 팀원이 된다.
  - 어기면 거절된다. 안내는 `거절: 승인 직전 검사에서 같은 주 역할의 팀원이 있음` 같은 꼴이다.
- 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다. 대기 중인 지원을 미리 거절하지 않는다.
- 한 번 투표하면 바꿀 수 없다.
- 투표 단추의 `result`는 그 지원의 지금 상태(승인, 대기, 거절)로 시작한다.

### 4.6 필수 포함 역할 자리 계산 (FR-6)
- 지원자가 들어간 뒤의 팀원을 기준으로, 기획자와 웹 프로그래머를 **서로 다른 학생**에게 맡기는 최대 배정 수 `k`(0~2)를 구한다.
- 아직 채우지 못한 필수 포함 역할 수는 `2 - k`, 남는 자리 수는 `4 - (팀원 수 + 1)`이다.
- `남는 자리 < 2 - k`이면 막는다(승인 직전 재검사에서는 거절한다).
- 예 1: 주 역할 기획자, 보조 역할 웹 프로그래머인 학생 혼자 있는 팀은 `k = 1`이다.
- 예 2: 테스터와 발표자만 있는 팀에 보고서 작성자가 지원하면, 남는 자리 1개로 2개를 채울 수 없으므로 막는다.

### 4.7 다른 사람의 변경 보기 (FR-7)
- `st.fragment(run_every=3초)`로 팀 목록, 투표 단추, 지원 상태, 관리자의 팀이 없는 학생 표시를 자동으로 다시 그린다(5초 이하).
- 바뀐 부분만 다시 그리므로 화면 전체가 깜빡이지 않는다.

### 4.8 모집 마감 (FR-8, 관리자)
- "모집 마감"(`admin_close`)을 누르면 마감 표시를 저장한다. 그 뒤로는 지원과 투표를 할 수 없다.
- 대기 중인 지원은 모두 거절하고 이유를 "모집 마감"으로 남긴다.
- 1명뿐인 팀의 학생은 팀에서 빠진다.
- 팀이 없는 학생의 이름을 `unassigned`에 보여 준다.
- 안내는 `승인: 모집을 마감함 (거절 N건, 팀에서 빠진 학생 M명)`이다.

### 4.9 배정 (FR-9, 관리자)
1. **가능성 판정**: 기존 팀원은 옮기지 않고 팀이 없는 학생만 넣어서, 규칙을 모두 지키는 배정이 있는지 모든 경우를 따져 확인한다.
   - 없으면 AI를 부르지 않는다. `assign_status`에 "규칙을 지키는 배정이 없음"과 이유(예: "팀3에 웹 프로그래머를 맡을 학생이 없음")를 보여 준다.
2. **AI 호출**: 1차, 2차, 3차 모델 순으로 부른다. 보내는 내용은 지금 팀 구성, 팀이 없는 학생과 역할, 규칙이다. 응답은 JSON 배정안으로 받는다.
   - 모델 하나를 부른 때부터 응답을 다 받을 때까지 **전체 120초**가 넘으면 끊고 다음 모델로 넘어간다.
   - 응답 없음, HTTP 오류(429 등), 빈 응답, JSON 형식 오류, 검사 실패를 모두 실패로 보고 다음 모델로 넘어간다.
   - `assign_status`에 "2차 모델(이름)의 응답을 기다리는 중 (n초)"처럼 몇 차 모델을 기다리는지 보여 준다.
3. **배정안 검사 5가지**:
   1. 팀이 없는 학생이 빠짐없이 배정됨
   2. 한 학생은 한 팀에만 배정됨
   3. 모든 팀이 2~4명
   4. 팀 안에서 주 역할 중복 없음
   5. 필수 포함 역할 충족
4. **앱이 스스로 배정**: 3차까지 실패하면 백트래킹으로 모든 경우를 따져 검사 5가지를 모두 통과하는 배정을 찾는다.
5. **보여 주기와 확정**: 검사를 통과한 배정안만 보여 준다(학생 이름, 역할, 배정된 팀, 어느 모델이 냈는지 또는 앱이 냈는지). 관리자가 "확정"(`admin_confirm`)을 누르면 팀원으로 DB에 저장한다.
6. AI 호출마다 결과(모델, 성공/실패 이유, 걸린 시간)를 `tf_ai_logs`에 남기고 관리자 화면에 보여 준다. README의 실패 사례 근거로 쓴다.

### 4.10 관리자 결과 안내
관리자 단추 4개(명단 올리기, 마감, 배정, 확정)의 `result`는 해냈으면 `승인`, 하지 못했으면 `막힘`으로 시작한다.

## 5. 화면 key 표 (공고 2.7절, 그대로 지정)

| 요소 | Streamlit | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 로그인 단추 | `st.form_submit_button` | `login_submit` |

| 결과 안내 | `st.container` | `result` |

| 지원 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 찬성 단추 | `st.button` | `vote_yes_{지원자 학번}` |
| 거부 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 처음 상태 만들기 | `st.button` | `admin_start` |
| 모집 마감 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시 | `st.container` | `unassigned` |
| AI 배정 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 | `st.button` | `admin_confirm` |

자동 갱신(어려운 해결)을 쓰므로 `refresh` 단추는 두지 않는다. `result`의 첫 단어는 반드시 승인, 대기, 거절, 막힘 중 하나다.

## 6. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 보안 | `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 `.env`(로컬)와 Streamlit Secrets(배포)에만 둔다. 코드, 깃허브, 화면, 로그에 출력하지 않는다. 오류 메시지에서도 DB 주소를 가린다. |
| 보안 | 비밀번호는 bcrypt 해시로만 저장한다. |
| 동시성 | `tf_members`의 `(team_id, slot_no)` 기본 키와 `student_id` 유일 제약으로 먼저 도착한 학생만 기록한다. 승인과 지원 처리는 팀 행 잠금(`SELECT … FOR UPDATE`)을 건 트랜잭션 안에서 한다. |
| 성능 | DB 연결 풀을 `st.cache_resource`로 한 번만 만들고 재사용한다. 화면 한 번 그릴 때의 질의 수를 줄인다(상태를 한 번에 읽음). |
| AI 한도 | 무료 모델은 하루 50회, 분당 20회까지다. 배정 한 번에 최대 3회 호출한다. 가능성 판정에서 불가능하면 호출하지 않는다. 채점 기간에는 하루 30회 이상 남겨 둔다. |
| 시간 | 배포 서버는 UTC이므로 화면의 시각은 한국 시각(KST)으로 바꿔 보여 준다. |
| 가용성 | GitHub Actions 예약 작업으로 매일 DB에 질의를 보내 Supabase 일시정지를 막는다. |
| 정직성 | 시나리오의 학생 이름이나 순서를 보고 결과를 정하는 코드를 쓰지 않는다. 모든 판정은 규칙으로만 한다. |

## 7. 고른 해결 방법 (공고 3장)

| 기능 | 선택 |
|---|---|
| 다른 사람의 변경 보기 | 어려운 해결: `st.fragment(run_every=3)` 자동 갱신 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결: 지원 단계에서 자리 계산으로 막음 |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결: 승인 직전 재검사. 투표가 끝난 순서로 처리 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결: DB 유일성 제약 + 팀 행 잠금 |
| AI 응답이 늦을 때 | 어려운 해결: 모델마다 120초 전체 대기 시간을 재서 끊음 |
| 3차 모델까지 실패 | 어려운 해결: 백트래킹으로 검사 5가지를 통과하는 배정을 끝까지 찾음 |
| AI 대기 중 화면 | 어려운 해결: 몇 차 모델(모델 이름)을 기다리는지와 경과 시간 표시 |
| DB 일시정지 막기 | 어려운 해결: GitHub Actions 예약 작업으로 매일 DB 질의 |

## 8. 범위 밖

- 학생이 역할을 바꾸는 기능
- 지원 취소, 투표 변경
- 팀 이름 바꾸기
- 확정 뒤 다시 편성하기(명단을 다시 올려 처음부터 시작함)

## 9. 완료 기준

- 부록의 연습용 시나리오 3개(쉬움, 중간, 어려움)를 배포한 앱에서 처음부터 끝까지 해 보았을 때, 단계마다 `result`의 첫 단어가 기대 결과와 같다.
- 확정 뒤 새 브라우저로 열어도 팀 구성이 남아 있고 규칙을 지킨다.
- AI 모델을 일부러 실패시켜도(잘못된 모델 이름, 짧은 시간 제한) 다음 모델로 넘어가고, 모두 실패하면 앱이 배정한다.
