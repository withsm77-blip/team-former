# 구현 계획: 팀 편성 웹 앱

PRD(`docs/PRD.md`)를 어떻게 만들지 정리한 문서다. 규칙 판정은 화면 코드와 분리해 순수 함수로 만들고, 테스트로 먼저 확인한 뒤 화면에 붙인다.

## 1. 기술 스택

| 구분 | 선택 | 이유 |
|---|---|---|
| 화면 | Streamlit (`st.fragment`, `st.container(key=…)`) | 과제 지정. 컨테이너 key로 채점 프로그램이 요소를 찾음 |
| DB | Supabase PostgreSQL, `psycopg` 3 + `psycopg_pool` | SQL 트랜잭션과 행 잠금으로 동시성 처리 |
| DB 주소 | Session pooler(포트 5432) | Streamlit Cloud는 IPv4만 지원하므로 Direct 주소 대신 pooler 사용. `prepare_threshold=None`으로 pooler와 호환 |
| 해시 | `bcrypt` | 공고 6.3절 |
| AI | OpenRouter Chat Completions API (`requests`) | 모델 3개를 순서대로 부름 |
| 비밀 값 | `st.secrets` → 없으면 `.env`(`python-dotenv`) | 로컬과 배포 모두 같은 코드 |
| 테스트 | `pytest` + 로컬 PostgreSQL 16 | 규칙과 시나리오를 자동으로 검증 |

## 3. DB 설계 (`schema.sql`)

| 테이블 | 핵심 열과 제약 |
|---|---|
| `tf_students` | `id` PK, `student_no` UNIQUE, `name`, `main_role`(6개 역할 check, 관리자는 NULL), `password_hash`, `is_admin` |
| `tf_student_sub_roles` | (`student_id`, `role`) PK, `role` check. 학생 1명에 0~2행 |
| `tf_teams` | `id`(=팀 번호) PK, `name` UNIQUE |
| `tf_members` | (`team_id`, `slot_no`) PK, `slot_no` check 1~4, `student_id` UNIQUE |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`(대기/승인/거절 check), `reason`, `created_at`, `decided_at`. **부분 유일 인덱스**: 학생당 `대기` 지원 1건만 |
| `tf_votes` | (`application_id`, `voter_id`) PK, `vote`(찬성/거부 check). PK로 투표 변경·중복 차단 |
| `tf_settings` | `key` PK, `value`. `closed`(마감 여부), `proposal`(배정안 JSON), `confirmed` |
| `tf_ai_logs` | AI 호출 기록: 차수, 모델, 결과, 이유, 걸린 시간 |

- 학생을 지우면 보조 역할, 팀원, 지원, 투표도 함께 지워지게 `ON DELETE CASCADE`를 둔다(초기화를 단순하게 하기 위함).
- RLS는 켜 두되 정책은 만들지 않는다. 앱은 DB 주인 계정으로 접속하므로 영향이 없고, Supabase 공개 API로는 테이블을 읽을 수 없게 된다.

## 4. 핵심 알고리즘

### 4.1 필수 포함 역할 매칭 `required_filled(members) -> 0..2`
- 학생마다 맡을 수 있는 역할 집합(주 역할 + 보조 역할)을 만든다.
- 기획자 후보 집합 P와 웹 프로그래머 후보 집합 W를 구한다.
- `P`, `W` 모두 비어 있지 않고 서로 다른 두 학생을 고를 수 있으면 2다. 즉 `|P ∪ W| ≥ 2`이면서 P와 W가 모두 비어 있지 않은 경우다.
- 그렇지 않고 하나라도 후보가 있으면 1, 아무도 없으면 0이다.

### 4.2 지원 검사 `check_apply(team_members, applicant) -> 막힘 이유 | None`
1. 팀원 4명이면 "팀이 꽉 참"
2. 주 역할이 같은 팀원이 있으면 "같은 주 역할의 팀원이 있음"
3. `after = members + [applicant]`이고 `4 - len(after) < 2 - required_filled(after)`이면 "필수 포함 역할을 맡을 학생의 자리가 모자람"

같은 함수를 **승인 직전 재검사**에도 쓴다. 이때 결과는 막힘이 아니라 거절이다.

### 4.3 투표 처리 (트랜잭션)
```
BEGIN
  SELECT … FROM tf_teams WHERE id = 팀 FOR UPDATE      -- 같은 팀 처리 직렬화
  지원 상태가 대기인지, 투표자가 지금 팀원인지, 마감 전인지 확인
  INSERT tf_votes (PK로 중복/변경 차단)
  거부  → 지원 거절 (이유: 팀원의 거부)
  찬성  → 지금 팀원 전원이 찬성했는가?
          아니오 → 대기
          예     → check_apply(지금 팀원, 지원자) 재검사
                    위반 → 거절 (이유: 승인 직전 검사: …)
                    통과 → 빈 slot_no에 INSERT tf_members, 지원 승인
COMMIT
```
투표가 끝나는 순간에 재검사하므로 처리 순서는 자연히 **투표가 끝난 순서**가 된다.

### 4.4 지원 처리 (트랜잭션)
팀 행 잠금 → 마감, 내 팀, 대기 지원 확인 → `check_apply` 순서로 진행한다.
- 빈 팀이면 지원(승인)과 팀원을 함께 기록한다.
- 팀원이 있는 팀이면 지원을 `대기`로 기록한다.

부분 유일 인덱스와 `tf_members.student_id` 유일 제약이 마지막 안전장치다. 위반 예외가 나면 막힘으로 안내한다.

### 4.5 마감
트랜잭션 하나로 처리한다.
1. `closed = true`로 저장한다.
2. 대기 중인 지원을 모두 거절한다(이유: 모집 마감).
3. 팀원이 1명인 팀의 팀원 행을 지운다.

### 4.6 배정안 검사 `validate(teams, unassigned, proposal) -> 위반 목록`
PRD 4.9의 다섯 가지를 각각 검사해 위반 문장을 모은다. 빈 목록이면 통과다. AI가 없는 학번이나 팀을 냈거나, 기존 팀원을 다시 적은 경우도 위반으로 본다.

### 4.7 가능성 판정과 백트래킹 `solve(teams, unassigned) -> 배정 | (None, 이유들)`
- 팀이 없는 학생은 많아야 8명이고 팀은 3~4개다. 경우의 수가 최대 4⁸ = 65,536이라 모든 경우를 따지는 것이 충분히 빠르다.
- 맡을 수 있는 역할이 적은 학생부터 놓아 탐색을 줄인다.
- 다음 경우에는 가지를 친다.
  - 팀 인원이 4명을 넘음
  - 주 역할이 중복됨
  - 남은 학생을 다 넣어도 2명이 안 되는 팀이 있음
  - 남은 학생 전체로도 필수 역할을 채울 수 없음
- 답이 없을 때의 이유는 팀별로 따로 따져서 만든다.
  - 그 팀에 넣을 수 있는 남은 학생 가운데 웹 프로그래머 후보가 없음 → "팀3에 웹 프로그래머를 맡을 학생이 없음"
  - 기획자도 같은 방식으로 따진다.
  - 학생 수 부족 → "팀이 없는 학생이 모자라 모든 팀을 2명 이상으로 만들 수 없음"
  - 팀별 이유를 찾지 못하면 "주 역할 중복 때문에 모든 조건을 함께 만족하는 배정이 없음"

### 4.8 AI 호출 `ai.assign()`
- 요청: `model`, `messages`(규칙, 팀 구성, 팀이 없는 학생을 JSON으로 전달), `max_tokens: 4000`, `reasoning: {"effort": "low"}`, `stream: true`
- 120초 전체 제한: 스트리밍으로 받으면서 조각을 받을 때마다 `time.monotonic()`으로 시작 뒤 경과 시간을 잰다. 120초가 넘으면 연결을 닫는다. 연결이나 읽기가 멈춘 경우에 대비해 별도 스레드에서 실행하고 `future.result(timeout=남은 시간)`으로 한 번 더 막는다.
- 응답에서 첫 `{`부터 마지막 `}`까지 잘라 JSON을 읽는다. 형식은 `{"assignments":[{"student_no":"…","team":1}]}`이다.
- 실패 종류: 시간 초과, HTTP 오류(429 등), 빈 응답, JSON 오류, 검사 실패. 하나라도 해당하면 다음 모델로 넘어간다.
- 진행 안내: 모델을 부르기 전에 `assign_status`에 "1차 모델(…)의 응답을 기다리는 중"을 쓰고 경과 초를 갱신한다.
- 3차까지 실패하면 `solve()` 결과를 쓰고 "앱이 스스로 배정함"을 표시한다.

## 5. 화면 설계

### 5.1 공통
- 로그인 전: `st.form` 안에 `login_student_no`, `login_password`, `login_submit`을 둔다.
- 로그인 뒤: `whoami`(이름, 학번, 역할), 로그아웃 단추를 둔다.
- `result`: 결과 안내는 `st.session_state`에 저장한다. 자동으로 다시 그려도 사라지지 않게 fragment 안 맨 위에 `st.container(key="result")`로 그린다. 안내의 첫 단어는 항상 승인, 대기, 거절, 막힘 중 하나다.

### 5.2 학생 화면: `@st.fragment(run_every=3)` 하나 안에 모두 그림
1. `result`
2. 내 상태(내 팀 또는 "아직 팀이 없음", 내 지원의 상태, 마감 여부)
3. 팀 카드 `team_N`: 팀원 이름, 주 역할, 보조 역할, "내 팀" 표시, 지원 단추 `apply_N`
4. 내 팀에 들어온 대기 지원 목록: `vote_yes_학번`, `vote_no_학번`, 또는 "내 투표: 찬성"

화면 상태는 한 번의 묶음 질의로 읽어 질의 수를 줄인다.

### 5.3 관리자 화면
- 명단: `admin_roster_file`, `admin_team_count`, `admin_start`
- 모집: `admin_close`
- fragment(자동 갱신): 팀 현황, `unassigned`
- 배정: `admin_assign`, `assign_status`, 배정안 표, `admin_confirm`, AI 호출 기록

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 무료 모델 응답 지연, 429, 빈 응답 | 120초 제한, 3개 모델, `reasoning effort low`, 마지막은 백트래킹 |
| AI 호출 한도 소진 | 개발 중 호출을 아끼고, 불가능 판정이면 호출하지 않음. 채점 이틀 전부터 호출 자제 |
| 자동 갱신 중 단추 클릭이 씹힘 | 상태를 DB 기준으로 다시 읽고, 단추 처리는 트랜잭션 안에서 다시 검사 |
| pooler 연결 끊김 | 연결 풀의 `check` 옵션으로 끊긴 연결을 버리고 다시 연결 |
| 로컬 네트워크가 DB 포트를 막음 | 개발 중에는 핫스팟을 쓰거나 로컬 PostgreSQL로 테스트. 배포 앱에는 영향 없음 |
| 비밀 값 노출 | `.gitignore`, 오류 메시지에서 DB 주소 가림, 커밋 전 `git diff` 확인 |
